# Play Console 등록과 스토어 등록 정보 (KAN-174)

Play Console에서 사람이 채워야 하는 값의 **정본**이다. 콘솔 화면은 기록이 남지 않아, 무엇을
어떤 근거로 답했는지가 여기 없으면 심사 반려나 데이터 안전 신고 불일치가 났을 때 되짚을 자리가
없다. 값이 바뀌면 콘솔과 이 문서를 같이 고친다.

콘솔 조작 자체는 자동화하지 않는다 — 등록비 결제, 본인 확인, 심사 제출은 계정 소유자가
직접 해야 하는 일이다. 레포가 맡는 몫은 **붙여 넣을 문안과 그 문안이 실제 동작과 맞는지의
근거**, 그리고 스토어 등록이 끝난 뒤 웹 CTA가 살아나는 결선이다.

20명이라고 적어 두고 있어 헷갈리는 자리다 — 콘솔이 표시하는 숫자가 정본이다.

### 테스터가 실제로 해야 하는 일

강제 요건은 둘뿐이다.

| | |
|---|---|
| 옵트인 | 초대 링크를 열고 테스터로 참여한다. **안드로이드 기기와 구글 계정이 둘 다 있어야 한다** |
| 14일 유지 | 그 기간에 옵트아웃하지 않는다. **나갔다 다시 들어오면 그 사람의 14일은 0부터 다시 센다** |

아이폰만 쓰는 사람은 머릿수에 넣을 수 없다. 옵트인은 구글 계정으로 하지만 설치는 안드로이드
기기라야 하고, 설치 없이 옵트인만 한 사람은 아래 서술형 답에 쓸 근거가 안 된다. 12명을 모으기
전에 안드로이드 기기 보유부터 확인한다.

에뮬레이터에 구글 계정 12개를 만들어 채우는 우회도 권하지 않는다. 프로덕션 액세스 신청서가
"테스터의 사용 패턴이 실제 사용자 행동과 비슷했는지"를 묻기 때문에, 같은 맥에서 돌린 계정
열두 개로는 그 칸에 쓸 말이 없다.

**매일 앱을 켜야 한다는 요건은 없다.** 구글 문서에 일일 사용 의무가 없다.

다만 사람만 채워 두고 아무도 안 쓴 테스트는 통과하지 못한다. 프로덕션 액세스를 신청할 때
서술형 답을 요구하는데, 항목이 "테스터가 앱의 모든 기능을 사용했는지", "테스터의 사용 패턴이
실제 사용자 행동과 비슷했는지"다. 여기 쓸 말이 없으면 신청이 반려된다.

그래서 테스터에게 부탁할 것은 이렇게 정리한다.

1. 링크로 참여하고 설치한다
2. 테스트를 한 번 완주한다 — 문장 읽기, 단어 문항, 결과 확인, 가능하면 카카오톡 공유까지
3. 한 줄 피드백을 남긴다 (신청서에 쓸 근거이자 KAN-39의 재료다)
4. 14일 동안 테스터에서 나가지 않는다

### 일정 — 비공개 테스트 시작일 D 기준

앞단은 끝났고, 시계를 움직이는 것은 **테스터 12명이 옵트인한 날 D** 하나다. D에 고정 날짜를
박지 않는 이유가 이번에 하나 더 늘었다 — **첫 비공개 테스트는 구글 심사를 거쳐야 테스터가
참여할 수 있다.** 심사가 언제 끝나는지는 우리가 정하지 못한다.

| 시점 | 일 |
|---|---|
| 2026-09-22 | 앱 레코드, Play App Signing(§2), 내부 테스트 배포, 앱 설정 11개, 등록 정보·자산, 비공개 테스트 **검토를 위해 Google에 전송** — 게시 개요 「검토 중」 |
| 심사 통과 | 최대 7일. 통과해야 비공개 테스트 참여 링크가 테스터에게 열린다 |
| D | 테스터 12명 옵트인 완료 — **심사 통과 뒤에야 셀 수 있는 날이다** |
| D+14 | 14일 충족. 프로덕션 액세스 신청 + 심사 제출 (신규 앱 심사 최대 7일) |
| D+21 | 스토어 게시 **최단** 시점. 테스터가 한 명이라도 빠지면 그 사람 몫만큼 D가 밀린다 |

내부 테스트 트랙은 이 심사와 무관하게 이미 살아 있다. AC "내부 테스트 트랙에서 팀 기기가
스토어 경유로 설치"는 그쪽으로 닫았다(§7 AC 대조표).

**테스터 12명이 이 티켓의 실제 임계 경로다.** 계정도 빌드도 다 준비돼 있어도 사람이 모이지
않으면 14일 시계가 시작하지 않는다. 옵트인 URL이나 구글 그룹으로 모으고, 명단은 계정 소유자가
관리한다. 팀원과 지인으로 채울 수 있는 규모다.

## 2. Play App Signing — 기존 키스토어를 앱 서명 키로 올린다

**결정: Play App Signing을 사용하되, 구글이 새 키를 만들게 두지 않고 `~/keys/accentury-release.jks`를
앱 서명 키로 업로드한다** (2026-09-07).

이 선택이 아니면 지문이 갈린다. 구글이 앱 서명 키를 새로 생성하는 쪽으로 등록하면 스토어가
재서명한 설치본의 인증서가 우리 키가 아니게 되고, `assetlinks.json`에 적힌 지문과 어긋나
**스토어에서 받은 앱만 딥링크가 조용히 깨진다** — 로컬 릴리스 빌드로는 재현되지 않는 종류의
고장이다 (`docs/wiki/app-links.md` "Play App Signing 지문"). 카카오 키 해시도 같은 문제를 겪는다.

기존 키를 올리면 얻는 것과 잃는 것.

| | |
|---|---|
| 유지되는 값 | `assetlinks.json` 지문 `48:C1:0D:…:FB:F2`, 카카오 키 해시 `mbUry3g8iSvbM3Ok5NlJ1ZYUIIo=` 둘 다 그대로 유효하다 |
| 얻는 것 | 앱 서명 키를 구글이 보관한다. 업로드 키를 잃어도 재발급 경로가 생긴다 — 지금은 키스토어 분실이 곧 영구 업데이트 불가다 (`docs/wiki/android-release-signing.md`) |
| 주의 | 업로드 절차에서 PEPK 도구로 키를 암호화해 올린다. 이때도 **원본 키스토어를 덮어쓰지 않는다** |

업로드 뒤 반드시 대조한다: Play Console › 테스트 및 출시 › 앱 무결성 › **앱 서명 키 인증서**의
SHA-256이 `assetlinks.json`의 값과 같은지. 다르면 구글이 새 키를 만든 것이므로, 콘솔에 표시된
지문을 Accentury_Server `infra/well-known/*/.well-known/assetlinks.json` 배열에 **추가**하고 (배열이라 여러 개를
넣을 수 있고 하나만 맞아도 검증은 통과한다) 게시 스크립트를 다시 돌린다. 카카오 콘솔의 키 해시도
같은 인증서에서 다시 뽑아 등록한다.

### 실제로는 이렇게 됐다 (2026-09-22)

**앱을 만든 시점에 이미 구글이 만든 앱 서명 키가 등록돼 있었다.** 2026-09-11 자동 생성된
SHA-256 `96:6D:40:05:…:92:86:38`이다. 새 앱은 Play App Signing이 기본이라 선택을 묻지 않고
구글 키를 배정한다. 그래서 위 계획대로 하려면 "등록"이 아니라 **키 교체**를 해야 한다.

출시 화면을 아무리 뒤져도 "기존 키 사용" 선택지는 없다. 경로는 여기다.

```
Google Play로 보호됨 › Play 스토어 보호 › 앱 서명 키 보호 › Play 앱 서명 관리
  (URL 끝이 …/keymanagement)
    → [키 변경] → 「Java 키스토어에서 키 내보내기 및 업로드」
```

그 화면이 주는 `pepk.jar`와 `encryption_public_key.pem`으로 키스토어를 암호화해 올린다.

```sh
java -jar pepk.jar --keystore=~/keys/accentury-release.jks --alias=accentury \
  --output=output.zip --include-cert --rsa-aes-encryption \
  --encryption-key-path=encryption_public_key.pem
```

**PEPK는 TTY가 없으면 죽는다.** 비밀번호를 `System.console()`로 직접 묻는데, Claude Code의 `!`
셸이나 그 밖의 비대화 셸에서는 그 값이 null이라 NPE로 끝난다. Terminal.app에서 사람이 직접
돌려야 하는 명령이다. 같은 자리에서 걸린 것이 하나 더 있다 — Terminal.app에 `~/Downloads`
읽기 권한(macOS TCC)이 없으면 다운로드한 jar가 "Unable to access jarfile"로 안 열린다.
`pepk.jar`와 pem을 `~/keys/`로 옮겨서 돌렸다.

업로드 결과는 콘솔 「디지털 애셋 링크 JSON」의 지문으로 확인했다 — `48:C1:0D:…:FB:F2`, §1
키스토어의 값 그대로다. **`assetlinks.json`도 카카오 키 해시도 손대지 않아도 된다.**

업로드 키는 새로 만들지 않고 같은 `accentury-release.jks`를 그대로 쓴다. CI가 쥐고 있는
시크릿이 그 키스토어라, 워크플로(`.github/workflows/app-release.yml`)는 고칠 것이 없다.

옛 구글 키가 서명한 설치본은 세상에 없다. 키를 바꾼 시점의 설치 수가 0이라 기존 사용자 업데이트가
깨질 걱정도 이번엔 없었다 — 설치 기반이 생긴 뒤였다면 키 교체는 훨씬 무거운 결정이다.

앱 이름에 브랜드만 넣지 않은 이유가 있다. `accentury`는 검색되지 않는 조어라, 이름에 "사투리",
"억양", "테스트"가 들어가야 스토어 검색에 걸린다. `strings.xml`의 `app_name`(런처 아이콘 아래
표시되는 이름)은 `accentury` 그대로 둔다 — 홈 화면에서는 짧은 쪽이 낫고, Play가 요구하는 것은
스토어 목록의 이름이지 런처 이름이 아니다.

2026-09-22 콘솔에 실제로 등록한 순서는 **브랜드가 앞**이다(`Accentury - 사투리 억양 테스트`).
검색어 세 개는 그대로 들어 있어 위 근거는 유지되고, 검색 결과 목록에서 잘릴 때 남는 쪽이
브랜드가 된다. 2026-09-07 초안은 순서가 반대로, 제품 설명이 앞이고 브랜드가 뒤였다.

### 자세한 설명 (4000자 제한, 현재 약 600자)

```
내 말투에 사투리가 얼마나 남아 있을까?

문장 몇 개를 소리 내어 읽으면 경남 사투리 억양을 점수로 재 드려요.
단어 문항까지 더해 억양과 어휘 두 축으로 보고, 다섯 등급 중 하나를 매겨요.

■ 이렇게 진행돼요
1. 마이크 권한을 허용하고 시작해요
2. 화면에 뜨는 문장을 소리 내어 읽어요 — 마음에 안 들면 다시 읽어도 돼요
3. 사투리 단어 문항에 답해요
4. 억양 점수, 어휘 점수, 그리고 내 등급을 확인해요

■ 결과는 이렇게 나와요
· 억양 점수와 어휘 점수를 따로 보여 줘요
· 다섯 등급 중 내 자리와 한 줄 총평을 받아요
· 결과 화면을 카카오톡으로 친구에게 보낼 수 있어요

■ 목소리는 남기지 않아요
녹음한 음성은 점수를 매기는 그 순간에만 쓰고 곧바로 지워요. 서버에 보관하지 않고
다른 곳에 보내지도 않아요. 회원가입도 로그인도 없어요.

경남 사투리로 먼저 시작해요. 다른 지역은 차차 넓혀 갈 계획이에요.
```

"목소리는 남기지 않아요" 문단은 장식이 아니다 — §5 데이터 안전 신고와 앱 내 마이크 고지가
같은 말을 해야 하고, 그 일치가 KAN-39의 AC "스토어 개인정보·마이크 권한 설명 일치"다.

## 5. 데이터 안전 섹션 답안

Play가 묻는 대로 답한 값과 그 근거다. **코드가 바뀌면 이 표부터 고치고 콘솔을 갱신한다** —
신고와 실제 동작이 어긋나는 것이 정책 위반이고, 앱이 내려가는 사유다.

### 데이터 수집·공유 요약

| 질문 | 답 | 근거 |
|---|---|---|
| 데이터를 수집하거나 공유하나 | 예 | 아래 여섯 종류 |
| 제3자와 공유하나 | **예** (2026-09-21 갱신) | Google AdMob에 광고 식별자·IP·기기 정보·노출/클릭 기록이 간다 (KAN-196, 방침 2항 제3자 제공 표 — Accentury_Server `docs/wiki/privacy-policy.md` §2 확정 답안). Firebase(Analytics·Crashlytics)와 Slack(후기 알림)은 우리 대신 처리·전달하는 **서비스 제공업체**라 Play 정의상 이 항목에 잡히지 않는다 |
| 전송 중 암호화하나 | 예 | 앱↔서버 전 구간 HTTPS |
| 데이터 삭제 요청 방법을 제공하나 | **예** (2026-09-21 갱신) | 방침 6항이 후기 회신 이메일을 적은 이용자에게 그 주소로 열람·삭제를 요청할 경로(13항 문의처)를 약속했다 (KAN-211, Accentury_Server `docs/wiki/feedback.md` §8). 2026-09-07 「아니요」의 근거였던 「사람을 특정할 값이 없다」는 회신 이메일이 생기며 깨졌다 |

이력: 2026-09-07 초안은 제3자 공유·삭제 요청 둘 다 「아니요」였다. 광고 사업자 확정(KAN-196,
2026-09-11)과 이용 후기(KAN-211, 2026-09-15)가 Dev에 들어와 바뀌었고, 초안 대비 표는
Accentury_Server `docs/wiki/privacy-policy.md` §2가 이력으로 들고 있다.

**2026-09-22 콘솔 입력 완료.** 아래 여섯 종류에 쓴 카테고리 이름이 콘솔 화면에 그대로 있었다 —
「기기 또는 기타 ID」, 「개인 정보 › 이메일 주소」, 「앱 활동 › 기타 사용자 생성 콘텐츠」. 이 문서의
라벨이 곧 콘솔의 라벨이다.

「일시적으로만 처리되며 저장되지 않음」은 **①음성에만** 체크했다. ⑤이메일과 ⑥후기는 서버에
1년 남으므로 체크하지 않는다 — 여기 잘못 체크하면 `FeedbackRetention`의 1년 보관과 신고가
어긋나고, 그 불일치가 곧 정책 위반이다.

음성 「공유됨」도 체크하지 않았다. 오디오는 우리 AWS 스택 안에서만 움직이고, AWS는 Play 정의상
우리 대신 처리하는 **서비스 제공업체**라 제3자가 아니다 — Firebase·Slack을 이 항목에서 뺀 것과
같은 이유다.

### 수집한다고 신고하는 것

**① 음성 또는 사운드 녹음** — 수집됨, 목적 "앱 기능", **일시적으로만 처리되며 저장되지 않음**에
체크, 선택사항 아님.

근거는 KAN-27이다 (Accentury_Server `ai/app/tempstore.py`). 추론 라이브러리가 파형 파일을 읽어야 해서 오디오가
디스크를 한 번 거치지만, 세 겹으로 막는다: 소유자 전용(700) 전용 디렉터리, 요청이 성공·실패·예외·
취소 어느 쪽으로 끝나도 `finally`에서 삭제, 그리고 프로세스가 kill돼 그 삭제가 실행조차 못 된
경우를 대비한 30분 청소 잡. 로그에도 경로와 파일명을 남기지 않는다. 서버 DB에 음성은 들어가지
않는다 — `TestSession`·`TestResult`·`VocabAnswer` 어디에도 오디오 컬럼이 없다.

**② 앱 상호작용** — 수집됨, 목적 "분석", 선택사항 아님.

Firebase Analytics로 익명 이벤트를 보낸다 (KAN-33). 이벤트 이름과 파라미터의 정본은
`web/src/analytics/events.ts`와 `app/src/main/java/com/accentury/app/analytics/AppEvents.kt`이고,
`item_shown`·`test_completed`·`share_clicked`·`tier_assigned` 같은 화면 사건이 전부다.
**세션 id, 세션 토큰, 문항 내용, 점수 원값은 파라미터에 싣지 않는다** — 그게 AppEvents의 명시적
규칙이고, 예외는 `tier_assigned`의 등급 코드와 10점 단위로 뭉갠 점수 버킷 하나뿐이다.

**③ 비정상 종료 로그** — 수집됨, 목적 "분석", 선택사항 아님.

Firebase Crashlytics다 (`app/build.gradle.kts`). 스택 트레이스와 기기 정보가 올라간다.

**④ 기기 또는 기타 ID (광고 ID)** — 수집됨, 목적 "광고 또는 마케팅", **공유됨**(Google AdMob),
선택사항 아님. (2026-09-21 추가)

Google AdMob SDK다 (KAN-196, `docs/wiki/ads-admob.md`). 분석 대기 화면 전면 광고와 재응시 전
보상형 광고 두 자리에서 광고 요청에 GAID가 실린다. 동의는 인트로 첫 실행 동의 시트에서 받고,
거부하면 비맞춤 광고(`npa=1`)만 나가는데 — **npa도 식별자를 빈도 제한·집계 보고·부정 사용 방지에
쓴다** (Accentury_Server `docs/wiki/privacy-policy.md` §1 10항 근거 행, Google 「맞춤 광고 및 맞춤 설정되지 않은
광고」). 그래서 "동의하면 수집"이 아니라 광고가 나가는 한 수집이고, 선택사항에 체크하지 않는다.
매니페스트의 `google_analytics_adid_collection_enabled=false`는 그대로다 — 그 키는 GA4 계측에
광고 ID를 붙일지를 정할 뿐이고 AdMob SDK는 자기 경로로 GAID를 읽는다 (`docs/wiki/ads-admob.md`
§6). 계측은 여전히 익명이고, 이 항목은 AdMob 몫이다. 웹 AdSense(KAN-197)는 브라우저 전용이라
Play 신고와 무관하다 (Accentury_Server `docs/wiki/privacy-policy.md` §6 마지막 항목).

**⑤ 개인 정보 › 이메일 주소** — 수집됨, 목적 "앱 기능"(후기 회신), **선택사항**, 공유 안 함.
(2026-09-21 추가)

이용 후기의 회신 이메일이다 (KAN-211, Accentury_Server `docs/wiki/feedback.md`). 결과 화면 후기 시트에서
이용자가 직접 적는 선택 입력이고, 안 적으면 수집이 없다. 서버 DB `session_feedback`에 **1년**
보관 뒤 자동 삭제 (`FeedbackRetention`). 슬랙 `#feedback` 알림에는 유무만 붙고 값은 싣지 않으며
(`FeedbackSlackNotifier`), 로그도 `LogMasking`이 가린다. 이 서비스가 받는 유일한 개인 식별
정보라 위 요약 표의 「삭제 요청 방법 제공」이 예로 바뀌었다.

**⑥ 앱 활동 › 기타 사용자 생성 콘텐츠** — 수집됨, 목적 "앱 기능", **선택사항**, 공유 안 함.
(2026-09-21 추가)

같은 후기의 별점(선택)·본문(1~500자, 필수)이다. 후기 보내기 자체가 선택이라 항목은
선택사항이다. 세션당 1건, 1년 보관, 저장 시점의 등급·테스트/점수 버전·플랫폼·트래픽을 함께
복사한다(세션과 FK 없음). 본문은 슬랙 `#feedback`으로 전달되지만 Slack은 우리 대신 전달·보관하는
**서비스 제공업체**라 Play 「제3자 공유」에는 잡히지 않는다 — 방침 4항이 Slack을 국외 이전으로
분류한 것과 어긋나는 게 아니라, 방침(개인정보 보호법)의 분류와 Play 신고의 정의가 다른 것뿐이다.
다른 이용자에게 보이는 게시물이 아니므로 §6 「사용자 생성 콘텐츠 공유」는 여전히 없음이다.

### 수집하지 않는다고 신고하는 것

| 항목 | 왜 |
|---|---|
| 이름·전화번호 | 회원가입도 로그인도 없다 |
| 이메일 주소 (계정용) | 회원가입이 없어 계정 이메일은 없다. 다만 **후기 회신 이메일은 위 ⑤로 선택 수집**한다 — 「이메일 주소」 항목은 수집함에 체크하고 선택사항 표시로 구분한다 |
| 사용자 ID | `setUserId`를 부르는 곳이 없다 (`AndroidManifest.xml` 주석). AdMob 도입 뒤에도 그대로다 |
| 위치·연락처·사진·파일 | 권한 자체를 선언하지 않는다 |
| 결제 정보 | 앱 내 결제가 없다 |

서버가 저장하는 것은 세션 행(id, 토큰 **해시**, 테스트 버전, 플랫폼, 앱 버전, 캠페인 토큰,
만료 시각), 결과 행(점수 셋과 등급), 단어 답변 행(문항 id, 고른 선택지, 정답 여부), 그리고
후기 행(별점, 본문, 회신 이메일, 결과 스냅샷 — Accentury_Server `backend/…/db/migration/V12__session_feedback.sql`)이다.
후기의 회신 이메일을 빼면 사람을 가리키는 값이 없어 Play가 정의하는 "개인 정보"에 해당하지
않는다. 세션 토큰은 원문이 아니라 해시로 들어가고 TTL 30분이 지나면 무효가 된다
(Accentury_Server `backend/…/session/TestSession.java`). 세션·결과는 24시간 뒤 정리되고 후기만 1년 남는다.

## 6. 콘텐츠 등급과 타겟 대상

| 질문 | 답 |
|---|---|
| 앱 카테고리 | 엔터테인먼트 |
| 폭력·성적 내용·욕설·약물·도박 | 전부 없음 |
| 사용자 간 상호작용 | 없음 (다른 사용자와 소통하는 기능이 없다) |
| 로그인 필요 | 없음 — 심사자에게 줄 테스트 계정도 없다 |
| 정부 앱 · 금융 기능 · 건강 앱 | 전부 아니요. 억양 점수는 의학적 판정이 아니다 |
| 사용자 생성 콘텐츠 공유 | 없음 — 결과 카드를 카카오톡으로 보내는 것은 사용자 본인이 자기 결과를 밖으로 내보내는 행위이고, 앱 안에 다른 사람에게 보이는 게시물이 생기지 않는다 |
| 광고 포함 | **예** (2026-09-21 갱신) — Google AdMob 전면 광고(분석 대기 화면)와 보상형 광고(재응시 전) 둘 (KAN-196, `docs/wiki/ads-admob.md` §5). 2026-09-07 초안은 아니요였고 콘텐츠 등급 설문을 이 답으로 다시 낸다 |
| 타겟 연령 | **18세 이상만 체크** (2026-09-22 등록) |
| 예상 등급 | 전체이용가 |

콘솔에서 이 설문의 이름은 「타겟층 및 콘텐츠」이고, 5단계 마법사로 진행한다. 연령대는 여러 개를
고를 수 있는 체크박스인데 **18세 이상 하나만 골랐다.**

2026-09-07 초안은 하한을 13세로 잡았다. 13~17을 포함하면 아동·청소년 대상 앱으로 분류돼 추가 심사가
붙고, 광고 SDK와 데이터 처리에 별도 요건이 생긴다. AdMob의 아동 대상 플래그를 끈 상태
(`docs/wiki/ads-admob.md`)와도 18+ 쪽이 정합적이다 — 청소년을 포함해 놓고 광고는 성인 기준으로
내보내면 그 자체가 불일치다.

미성년을 대상에서 빼는 이유는 콘텐츠가 아니라 요건 쪽이다. 아동 대상으로 신고하면 가족
정책(Families Policy)이 걸리고 광고·SDK·데이터 처리에 별도 심사가 붙는데, 음성을 받는 앱이
그 심사를 통과하려면 부모 동의 흐름이 필요하다. 콘텐츠 자체는 전체이용가이므로 18세 미만이
받는 것을 막지는 않는다 — 타겟층 신고는 "누구를 겨냥해 만들었나"이지 연령 제한이 아니다.

## 9. 이월

- ~~**prod에서 음성 문항이 「분석 실패」로 떨어진다 (조사 중).**~~ **해결 (2026-09-22)** —
  prod는 정상이다. CloudWatch로 그날 세션을 되짚은 결과 「분석 실패」의 정체는 `ANALYSIS_MISREAD`,
  즉 **제시 문장과 다른 발화**라는 판정이었다. 가짜 마이크 빌드가 열 문항 내내 같은
  `fake_mic.wav`(80044B) 한 벌을 올리니 AI가 정확히 그렇게 읽은 것이다. 2026-09-20의 실제 발화
  세션은 음성 5문항이 모두 통과했다. 같이 보였던 「다시 녹음이 필요해요」는 회로 차단의
  잔상이다 — 05:19:04에 열렸다가 45초 뒤 닫혔다. **12명 실기기 테스트를 막는 장애는 없다.**
- **무음·극단 입력이면 AI가 500을 낸다 (부수 발견, P2 후보).** 위를 쫓다 나온 것이다. 분석값이
  `NaN`이 되면 JSON 직렬화에서 터져 500이 나가고, 백엔드가 3회 재전송한 뒤 회로를 연다
  (2026-09-17·2026-09-22 재발). 자리는 Accentury_Server `ai/app/track1.py` 615행 근처다.
  실사용에서는 마이크가 무음만 담는 경우가 드물어 12명 테스트의 선결 조건은 아니다 — 별도
  티켓으로 뺀다.
- **에뮬레이터 완주 검증에는 문항별로 다른 WAV가 필요하다.** `app/src/debug/java/com/accentury/app/audio/PcmSources.kt`가
  `-PfakeMic`로 받은 에셋 **한 개**를 모든 문항에 물린다. 그래서 prod를 겨눈 가짜 마이크 완주는
  구조적으로 불가능하다 — 문항 문장별 WAV를 골라 먹이도록 고치거나, AI 스텁을 띄운 로컬
  스택으로 찍는다 (`docs/wiki/app-icon-assets.md` §7 `04-result` 재촬영).
- **`04-result` 스크린샷 실기기 재촬영.** 위 문제가 닫히거나 실기기에서 사람이 직접 완주하면
  갈아 끼운다 (§3).
