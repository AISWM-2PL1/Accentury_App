# 웹 배포 범위 (KAN-344, App Store 2.5.2)

앱 화면 대부분은 WebView가 `https://accentury.app`에서 불러오는 웹이라, 웹만 배포해도 심사받은 바이너리의 동작이 바뀐다.
App Store 가이드라인 2.5.2는 앱이 심사 뒤 기능을 바꾸는 코드를 내려받아 실행하는 것을 금한다. 그래서 **웹 단독 배포로 낼 수 있는 것과
새 빌드를 타야 하는 것**을 나눈다(2026-11-10 자체 감사, KAN-344-7).

| 웹 단독 배포 (Dev→Release 승격으로 prod 반영) | 새 네이티브 빌드 + 심사 메모 갱신과 함께 |
|---|---|
| 버그 수정 — 심사받은 동작으로 되돌리거나 깨진 화면을 고치는 것 | 새 화면·새 탭·새 기능(학습 종류 추가, 번역 방향 추가 같은 것) |
| 콘텐츠 — 문항·학습 세트·카드처럼 서버 발행본이 바뀌는 것 | 새 브리지 메서드를 쓰는 화면(웹이 메서드 유무로 갈라도 마찬가지다) |
| 문구·카피·접근성·디자인 다듬기 — 기능의 범위가 그대로인 것 | 개인정보·동의·광고·추적 흐름이 바뀌는 것(심사관이 확인한 동작이 바뀐다) |

판정이 애매하면 새 빌드 쪽으로 둔다. 새 기능의 웹을 먼저 prod에 올려야 하면(빌드와 같은 날 심사에 들어가야 하는 경우) 그 화면은 그 기능을
아는 빌드에서만 열리게 한다 — 예: 브리지 메서드 유무로 가르는 기존 패턴(`webview-bridge.md` §1). 그 빌드의 심사 메모(`app-store-listing.md` §8)에
기능과 확인 경로를 적는다.

승격 PR 템플릿(`.github/pull_request_template.md` 「검증」)에 이 규칙의 체크 줄이 있다.

## 예외 기록

규칙을 따르지 않고 승격하는 경우는 여기에 적고, 승격 PR의 체크 줄에는 이 절을 가리킨다.

### 2026-11-10 — KAN-330 승격 (PR #70, 팀 결정)

| 예외 항목 | 규칙대로라면 | 이번에 하는 것 |
|---|---|---|
| iOS 광고 사전 시트의 [계속] 하나(`web/src/ads/AdConsentSheet.tsx`, webview-bridge §8.7) | KAN-330 브리지(`getAccountKind`)를 아는 빌드에서만 [계속] 하나, 옛 빌드는 두 선택지 | 브리지로 가르지 않는다. UA가 iOS 앱이면 빌드와 무관하게 [계속] 하나 |
| 번역 결과의 [부적절한 결과 신고] 버튼(KAN-344) | 새 빌드와 함께 | 빌드와 무관하게 보인다 |
| 게스트 UI(홈 레벨 테스트 카드·학습 로그인 안내, `GuestLoginPrompt`) | 새 빌드와 함께 | 그대로 승격한다 |

**이유.** App Store에 승인된 iOS 빌드가 아직 없다(빌드 13·15 거절, `app-store-listing.md` §11). 그래서 옛 빌드가 [계속] 하나를 받는 영향은
TestFlight 빌드에 그친다 — 그 빌드들은 ATT를 거부해도 저장값 `granted`면 npa 없이 요청하고 「일반 광고만 보기」를 고를 길이 없지만,
일반 사용자에게 배포된 빌드가 아니다. 신고 버튼은 서버 API(`POST /v0/translations/reports`, 서버 Dev에 병합됨)만 있으면 되고 네이티브가 할 일이
없다. 게스트 UI는 `getAccountKind`가 `'guest'`일 때만 그려지는데, 그 값은 KAN-330을 아는 빌드만 준다 — 옛 빌드에서는 예전 화면 그대로다.

**다음부터.** 승인된 iOS 빌드가 생긴 뒤의 승격에는 이 예외를 쓰지 않는다. iOS 시트를 다시 고칠 일이 생기면 브리지 메서드 유무로 가르는
방법(PR #70 리뷰 인라인 코멘트)을 따른다.
